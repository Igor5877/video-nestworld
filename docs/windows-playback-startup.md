# Перевірка запуску відео на Windows, 2026-10-18

## Спостереження

На Windows 11, Intel Iris Xe, Forge 47.4.28, WaterMedia 2.1.37 перший запуск
HLS-потоку перейшов з `NOTHING_SPECIAL` у `ENDED` без відеотекстури.
Повторний запуск користувачем запрацював. Плейлист відповідав HTTP 200;
окремий тест вбудованого VLC 3.0.18 відтворював першу серію каталогу.

Точна причина першого переходу в `ENDED` не встановлена: лог Minecraft не
містив подробиць нативного VLC для цієї спроби. Не можна стверджувати, що це
виключно помилка драйвера, Windows чи конкретного відеохостингу.

## Підтверджені дефекти

- WaterMedia `BasePlayer.isReady()` викликає `StatusApi.isPlayable()`, а той —
  `libvlc_media_player_will_play()`. Цей прапорець буває true вже в `OPENING`.
- Старий Display надсилав seek/unpause до першого кадру. Окремий Java-тест із
  реальною WaterMedia, callback-поверхнею та тим самим потоком відтворив ранні
  команди в `OPENING`. Запит seek на 5000 мс губився: відтворення починалося з 0.
  У двох спробах з очікуванням першого кадру seek застосувався до 5000 мс.
  Сам початковий `ENDED` цим тестом стабільно не відтворено.
- `setPauseMode()` мовчки нічого не робить, коли VLC `canPause()` повертає false,
  але старий Display уже позначав команду виконаною.
- У WaterMedia 2.1.37 `preRender()` просто повертає ID виділеної текстури,
  навіть коли кадрів ще немає. Це не доказ успішного старту.
- Раніше після раннього `ENDED` не було автоматичного повторного запуску.

## Чому поведінка Linux може відрізнятися

У JAR WaterMedia є різні файли `videolan/arguments.json` і
`videolan/arguments_linux.json`. На цьому Windows використано вбудований VLC
3.0.18 з `direct3d11,glwin32,gl,any`, `d3d11va,dxva2,any`, `avcodec-fast` та
`avcodec-skip-idct=4`. Linux-конфігурація не задає ці параметри; бібліотека VLC
постачається окремо. Це різні середовища та порядок подій запуску.
Версію VLC й журнали Linux-машини не перевірено: відсутність збою там не доводить
відсутності помилки раннього керування у спільному коді.

## Зміни 1.3.11 та перевірка

Display чекає нативного кадру і стану PLAYING/PAUSED перед керуванням; підтверджує
паузу фактичним станом; не віддає текстуру до виконання callback завантаження.
Якщо до першого кадру отримано ENDED/ERROR, через секунду виконується одна
повторна спроба з актуальною запитаною позицією. Пауза користувача блокує retry,
а завершення після декодованих кадрів не перезапускає ролик.

Регресійний тест компілює справжній Display із керованими підмінами Minecraft
та WaterMedia. Він перевіряє ранні команди, відкладену паузу, перший кадр,
збереження позиції, ліміт повторів і звичайне завершення:

```sh
python tools/test-display-startup.py
./gradlew build
```

Потрібен JDK 17+ у PATH; шляхи можна передати через `--javac` і `--java`.
Ці тести не замінюють перевірку нового JAR у Minecraft на Windows і Linux.
