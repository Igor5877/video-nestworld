# Світло кімнати від відео під шейдерами - етап 2 (перевірка, не реалізація)

Етап 1 (патч BSL: самосвітний матеріал екрана) - у `docs/SHADER_PATCH.md`. Тут - що показала перевірка того, як дані
про кадр можна передати в BSL через Oculus і як шейдер обліковує перешкоди. Нічого з цього ще не реалізовано.

Перевірено читанням коду Oculus 1.8.0 (`IrisApi`, `Iris`) і BSL v10.1.1 (`shadow.glsl`, `voxelMap.glsl`,
`shadowcomp`, `coloredBlocklight.glsl`, `block.properties`). У пісочниці це не запускалося.

## 1. Які канали даних "мод -> шейдер" існують

| Канал | Висновок |
|---|---|
| Публічний API Oculus (`net.irisshaders.iris.api.v0`) | Лише `isShaderPackInUse`, `isRenderingShadowPass`, `getConfig`, `getSunPathRotation`, текстові вершини, `IrisItemLightProvider` (колір світла **предмета в руці**). Власних uniform-ів чи текстур для пака API не дає. |
| Власний uniform / текстура з мода | Немає легального шляху: uniform-и описує сам пак (`shaders.properties`), зовнішні текстури вантажаться лише з паку. Лізти у внутрішні класи Iris (`CustomUniforms`, `ImageHolder`) - крихко між версіями. |
| Стан блока (`blockEntityId` / `mc_Entity`) | **Працює.** Пак бачить id блока з `block.properties`, а для стану блока - окремий id (`block.26007=nestworldvideo:video_screen:hue=7`). Це єдиний канал, який Oculus гарантує. |
| Освітленість (`lmCoord`) | Ванільний блок-світло: яскравість `LIT` (рівень 10) модом вже керується, колір - ні. |

## 2. Як BSL обліковує перешкоди

- BSL (режим `MULTICOLORED_BLOCKLIGHT`) на shadow-проході пише в 3D-текстуру (voxel map) **останні дві цифри id**
  кожного блока в зоні навколо гравця (`UpdateVoxelMap`, лише геометрія terrain: solid/cutout/translucent).
- `shadowcomp` розтікає світло по цьому об'єму (flood-fill) і враховує: `99` - непрозорий блок (перешкода),
  `51-74` - прозорий блок із тонуванням, `01-25` - яскраве джерело певного кольору, `26-50` - тьмяне.
- Тобто **перешкоди вже рахує сам BSL** (стіни, кути, прозорі блоки). Мод свій розрахунок для цього не потрібен.
- Обмеження: зона `voxelDistance = 32` блоки, лише блоки (сутності та блокові сутності - ні), 25 кольорових класів
  на джерело, колір - від id блока, а не від текстури.

## 3. Що з цього випливає для світла від відео

1. Дані про кадр можна передати лише через **стан блока**: модові плитки екрана отримують властивість `hue` (0-24)
   і яскравість, а `block.properties` (у патчі) зіставляє кожен стан з кольоровим класом BSL.
2. Перешкоди, поширення і м'якість світла дасть BSL; ні "решітки кольорів 32x18", ні власних face-накладок не буде -
   це приблизно один колір на плитку (або на невелику групу плиток).
3. Ціна: кожна зміна кольору = оновлення стану блока = перебудова секції чанка на клієнтах. Реально лише раз на
   0,5-1 с і для обмеженої кількості плиток; плавності "за кадром" не вийде.
4. Працює лише в режимі `MULTICOLORED_BLOCKLIGHT` пака (його вмикає користувач). Мій патч зараз для bloom-маски
   використовує `colortex8` саме коли цей режим вимкнений - у режимі MCBL маска вимикається, нічого не конфліктує.

## 4. Що запропоновано перевірити першим (етап 2)

1. Увімкнути MCBL у BSL і поставити пробний блок із `block.26007`: чи світить кольором, чи відсікається стінами.
2. Змінити стан блока щосекунди і виміряти вартість (FPS, трафік чанків, затримку).
3. Лише після цього вирішувати, чи залишати власні накладки мода як запасний режим для паків без MCBL.

## 5. Накладки мода під час перевірки

Власне кольорове світло мода (`screen_glow`) і блок-світло (`light_when_playing`) вимкнені в тестовому сценарії
`-Pguidisplay`, щоб ефекти не подвоювалися. У грі користувач вимикає їх у налаштуваннях моду, поки перевіряє
нове освітлення.
